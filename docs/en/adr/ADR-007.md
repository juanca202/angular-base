# ADR-007: Testing Strategy

**📖 **[**English**](./ADR-007.md)** | **[**Español**](../../es/adr/ADR-007.md)

**Status:** Accepted
**Date:** 2025
**Deciders:** Architecture Team

---

## Context

As the application grows, maintaining code quality and preventing regressions becomes critical. Without a well-defined testing strategy:

* Tests may be inconsistent in structure and quality
* Critical bugs might go undetected
* Refactoring becomes risky without test coverage
* Onboarding new developers is slower without test examples
* Integration issues are discovered late in development
* No clear guidelines on what to test and how

Additionally, the project makes heavy use of **Angular Signals** and **AI-assisted tooling** (Cursor, Copilot, etc.), which may incorrectly interpret signals as regular functions if no clear testing contract exists.

This ADR applies to **Angular 21+**, which ships with **Vitest integrated by default** via Angular CLI, as described in the official Angular testing guide.

We need a comprehensive testing strategy that:

* Ensures code reliability and maintainability
* Provides confidence when refactoring
* Serves as documentation for code behavior
* Catches bugs early in the development cycle
* Maintains consistent test quality across the team
* Avoids ambiguity when testing reactive state (Signals)

---

## Decision

We will use a **multi-layered testing approach** with:

1. **Unit Testing:** Vitest (integrated with Angular CLI in Angular 21+)
2. **Integration Testing:** Testing component-service interactions
3. **E2E Testing:** Playwright for end-to-end user workflows
4. **AAA Pattern:** Arrange, Act, Assert structure for all tests
5. **Test Coverage:** Aim for ≥80% branch coverage, focusing on critical paths
6. **Test Isolation:** Tests must be independent and deterministic
7. **Type Inference First:** TypeScript inference is preferred by default
8. **Signals Testing Contract:** Angular Signals must be treated as state containers, not functions

---

## Core Principles

### Type Inference First

The project favors **TypeScript type inference** over explicit typing to keep code concise and readable.

Explicit types MUST be introduced only when:

* Type inference is ambiguous
* Tooling (tests, IDEs, AI assistants) misinterprets intent
* Public APIs or architectural boundaries require clarity

Inference is the default. Explicit typing is a tool to remove ambiguity, not a requirement.

## Implementation

### Testing Stack

* **Vitest:** Unit and integration testing framework (built-in with Angular 21+)
* **Angular Testing Utilities:** TestBed, ComponentFixture
* **Playwright:** End-to-end testing framework

Tests are executed using the Angular CLI:

```bash
ng test
```

Test configuration (coverage, browser mode, watch mode) is managed by Angular CLI according to the official Angular testing guide.

## Unit Testing with Vitest

### AAA Pattern (Arrange, Act, Assert)

All tests must follow the AAA pattern:

```ts
it('should calculate total price correctly', () => {
  // Arrange
  const items = [
    { price: 10, quantity: 2 },
    { price: 5, quantity: 3 }
  ];
  component.items = items;

  // Act
  const total = component.calculateTotal();

  // Assert
  expect(total).toBe(35);
});
```

## Signals Testing Contract

Signals represent **state**, not behavior.

### Rules

#### MUST

* Signals MUST be read using `signal()`
* Signals MUST be updated using `set()` or `update()`
* Tests MUST assert signal values, not signal instances
* Signals MUST rely on type inference by default

#### MUST NOT

* MUST NOT spy on signals
* MUST NOT mock signals
* MUST NOT reassign signals
* MUST NOT treat signals as regular functions

---

### Signals and Type Inference

Signals SHOULD rely on inference:

```ts
customers = signal<Customer[]>([]);
```

Explicit generic types MUST be provided when:

* Signals are used in unit tests
* Signals cross architectural boundaries
* Signals are accessed by AI-assisted tooling

This ensures signals are clearly distinguishable from functions without introducing explicit `Signal<T>` typing.

## Testing Signals

```ts
describe('CustomerService', () => {
  let service: CustomerService;

  beforeEach(() => {
    service = new CustomerService();
  });

  it('should initialize with empty customers', () => {
    expect(service.customers()).toEqual([]);
  });

  it('should update customers signal', () => {
    const newCustomers = [{ id: '1', name: 'John' }];
    service.setCustomers(newCustomers);

    expect(service.customers()).toEqual(newCustomers);
  });

  it('should compute total count', () => {
    service.setCustomers([
      { id: '1', name: 'John' },
      { id: '2', name: 'Jane' }
    ]);

    expect(service.totalCount()).toBe(2);
  });
});
```

---

## Test Public APIs, Not Implementation Details

Signals are considered **state**, not implementation.

```ts
// ✅ Correct
expect(component.customers()).toEqual(mockCustomers);

// ❌ Incorrect
vi.spyOn(component, 'customers');
```

---

## Test Doubles

Only **behavior** may be mocked or spied.

```ts
const mockRepository = {
  findBy: vi.fn().mockReturnValue({
    load: vi.fn(),
    value: signal<Customer[]>([]),
    loading: signal(false),
    error: signal(null),
    destroy: vi.fn()
  })
};
```

Signals must always be real signals.

---

## AI-Assisted Testing Guidelines

When using AI tools (Cursor, Copilot, ChatGPT):

* Prefer inference, but add explicit generics to signals when needed
* Never accept generated tests that spy on or mock signals
* Review generated tests for signal misuse
* Signals must always be read with `()` and updated with `.set()`

## Test Coverage Goals

* **Branch Coverage:** ≥80% for critical paths
* **Function Coverage:** ≥80% overall
* **Line Coverage:** ≥80% overall
* **Focus Areas:** Business logic, error handling, edge cases

## E2E Testing with Playwright

```ts
test('user can login and view dashboard', async ({ page }) => {
  await page.goto('/signin');
  await page.fill('[formControlName="email"]', 'user@example.com');
  await page.fill('[formControlName="password"]', 'password123');
  await page.click('button[type="submit"]');

  await expect(page).toHaveURL('/dashboard');
});
```

## Consequences

### Positive

* Consistent and reliable test structure
* Safe refactoring with confidence
* Clear testing semantics for Signals
* Reduced errors from AI-assisted tooling
* Tests act as executable documentation

### Negative

* Slightly more discipline required in tests
* Learning curve around Signals semantics

### Mitigation

* Provide examples and templates
* Enforce rules via PR reviews
* Treat Signals as state, not behavior
